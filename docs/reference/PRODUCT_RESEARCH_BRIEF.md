## 0. 如何使用本文

本文不是让研究模型直接“设计一个播放器”，也不是让它为现有实现寻找合理性。它的任务是先回答：荧荧究竟应该围绕什么用户问题、内容对象和使用路径成立。

建议把本文完整交给具备联网检索能力的研究型模型，并要求它：

1. 区分仓库事实、用户亲历、产品推断和待验证假设；
2. 使用截至研究当日仍有效的一手资料核对竞品与 Android 平台能力；
3. 同时寻找支持和反驳当前方向的证据；
4. 先给出产品判断，再谈信息架构和功能；
5. 不把“播放器通常有什么”当作需求来源；
6. 不把当前已经实现的功能视为必须保留在主路径中的沉没成本；
7. 对无法从公开资料回答的问题，明确转化为用户研究或真机实验。

本文使用以下标记：

- **[F] 仓库事实**：可以从当前代码、文档、提交或真机记录核对；
- **[U] 用户亲历**：产品创建者的直接使用感受或判断；
- **[I] 推断**：基于事实形成的解释，仍可能被新证据推翻；
- **[H] 假设**：值得研究或实验，但当前没有充分证据；
- **[D] 暂定边界**：为避免当前讨论走偏而先固定的表达或范围，不代表研究后的最终产品决定；
- **[Q] 研究问题**：研究型模型需要回答或拆成验证方案的问题；
- **[E] 初步外部证据**：来自一手资料的起点，仍要求研究型模型按研究日期复核版本、适用范围和限制。

## 1. 研究任务摘要

### 1.1 产品背景

荧荧是一款 Android-first、OLED-first 的本地播放产品。它最早围绕一种非常具体的体验建立：在睡前、暗室、宿舍或其他不适合大面积亮屏的环境中，让媒体继续提供声音和时间，只在 OLED 纯黑屏幕上显示当前同步字幕。

早期内部定义是：

> 媒体提供声音和时间，字幕是正在发生的视觉内容，界面逐渐退场，最后只剩文字发光。

当前正式定义已经扩展为带有选择性内容库、队列、播放列表、睡眠定时、无字幕微光和系统媒体控制的本地播放器。扩展解决了真实的播放可靠性、内容组织和隐私问题，但也改变了产品重心。

### 1.2 新出现的关键信号

- **[U]** 产品创建者曾连续约一小时使用更早期的字幕中心版本，主观感受是“效果相当惊艳”。
- **[U]** 这种惊艳感不是来自当前选择性资源库版本，而是来自更早期、字幕与媒体联动更紧密的版本。
- **[U]** 当前版本明显缺少字幕的发现、关联和作为主内容的联动感。
- **[U]** 大范围扫描设备音频和视频未必符合真实使用意图；用户可能更愿意打开一个文件、选择一个文件夹，或只处理自己明确选中的小范围内容。
- **[U]** 在宿舍等集体居住环境中，很多人本来就会关灯使用手机。与普通整屏发光相比，只显示少量低亮字幕像素，直觉上更符合低干扰需求。

**[F]** 这次一小时体验对应的准确提交、媒体内容、字幕格式、单双语状态、窗口亮度、文字灰阶、设备、观看距离和环境光尚未形成记录。它是一条很强的方向信号，但还不是可复现实验。

这些信号把下一轮研究从“怎样补全本地播放器”改成了：

> 怎样让用户以最小摩擦找到或建立“媒体 + 同步文字”的可信关系，并尽快进入那个已经出现过强烈正向体验的微光状态？

### 1.3 研究需要支持的核心决策

研究最终必须支持以下决策，而不是只给竞品清单：

1. 荧荧的第一产品身份是“字幕夜读产品”还是“带微光能力的本地播放器”？
2. 产品首页的第一对象是“继续上次”“文件夹/会话”“资源库”，还是其他对象？
3. 首次打开新内容时，应该优先单文件、文件夹，还是设备媒体扫描？
4. “媒体条目”还是“媒体 + 字幕 + 进度”的播放会话，才是产品的基本对象？
5. 字幕应该如何被发现、匹配、预览、选择、切换、记忆和恢复？
6. 当前选择性资源库应保留为主路径、降级为可选能力，还是改造成轻量会话/文件夹历史？
7. 应该从 Apple Music 等歌词界面和开源播放器中借什么，又必须拒绝什么？
8. 下一轮应先设计什么，先做什么用户实验，哪些功能应暂停？

## 2. 健康与低发光叙事边界

这不是本轮产品研究的主问题，但需要先固定表述边界，避免研究和营销走偏。

- **[I]** 在观看距离、时长和文字可读性相当时，OLED 只点亮少量低亮字幕像素，整体发光量通常显著低于整屏发光界面；没有合理依据预期它比普通全屏亮界面产生更大的总体光刺激。
- **[E]** 屏幕与其他高专注近距离任务仍可能减少或改变眨眼，增加干涩和暂时性视觉疲劳；可参考[数字屏幕使用与干眼综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC8439964/)。OLED 的 PWM 调光可能产生可感知闪烁或视觉不适，但影响取决于设备调光方式、亮度、内容和个体，不能把所有 OLED 一概而论；可参考[OLED PWM 频率与亮度的闪烁研究](https://pubmed.ncbi.nlm.nih.gov/41411543/)和[闪烁与视觉不适研究](https://pubmed.ncbi.nlm.nih.gov/32474213/)。
- **[D]** 现有证据不足以把这种界面描述成医学意义上的“护眼”，也不应承诺防近视、改善视力或保证睡眠。
- **[D]** 产品语言应使用“减少发光面积”“低发光”“低干扰”“暗室可读”，不使用“护眼”“零伤害”或“零蓝光”。
- **[D]** 校准目标应是“清晰、舒适、不费力”，不是“越暗越好”或“暗到刚好还能辨认”。

研究模型可以补充健康声明边界，但不应让健康论证替代产品价值验证。核心价值仍是低干扰地继续理解内容。

## 3. 产品演变：从字幕会话到选择性资源库

### 3.1 M0B 交互原型：字幕是产品主角

**[F]** [`../../prototype/m0b-ui/index.html`](../../prototype/m0b-ui/index.html) 保存的早期交互原型具有以下特征：

- 首次体验从“只让字幕发光”的真实微光校准开始；
- 首页只保留两个主要决定：“继续微光”和“打开新的媒体”；
- 继续卡片明确显示上次时间位置和“SRT 双语”状态；
- 普通播放器中心是上一句、当前双语字幕和下一句；
- 字幕显示面板包含微光强度、字幕同步和双语开关；
- 微光同时拥有 primary 与 secondary 两个字幕层；
- 样片文案直接表达“字幕不是播放器的附件，而是今晚的内容”；
- 普通控制存在，但服务于定位、同步和进入微光，没有资源库维护任务。

这个版本建立的是一条很短的体验路径：

```text
首次校准
→ 继续微光 / 打开新媒体
→ 字幕中心的普通播放器
→ 只剩当前字幕的微光
```

### 3.2 M1 单会话版本：来源独立，字幕仍是主内容

**[F]** 在提交 `534951c` 附近，产品指南将荧荧定义为“会逐渐退场的 OLED 微光同步文字播放器”，并明确写出：

- 产品解决的不是“如何管理全部媒体”；
- Home 只保存一个最后会话，不建立完整媒体库；
- 播放源和字幕源是相互独立的槽位；
- 用户可以先选媒体，也可以先选字幕；
- 普通播放器以字幕语境为中心；
- 没有有效字幕时可以播放，但没有有意义的 Glow 阅读体验；
- 当前阶段明确不做媒体扫描、完整最近列表、媒体库、队列和随机播放。

这一阶段已经把后台播放、会话恢复、四类外挂字幕解析和亮度职责工程化，但产品对象仍然是：

```text
一个可恢复播放会话
= 一个媒体来源
+ 一个可选但视觉上核心的字幕来源
+ 播放位置、偏移、倍速和显示设置
```

### 3.3 当前版本：播放器完整性与内容库成为前置基础

**[F]** 2026-08-09 至 2026-08-10 的一组提交快速加入并重组了：

- `7f720e6`：OLED-first 视觉外壳，并允许无字幕进入微光；
- `efb10f7`：系统音频扫描、文件夹、单文件记忆、分类和播放列表；
- `90a4895`：队列与睡眠定时；
- `6592daa`：资源库成为默认首页，加入搜索、迷你播放器和来源管理；
- `6cdca60`：音视频统一成为候选，加入已收录、已忽略、首页内容集和字幕匹配关系；
- `0948a0d`：正式指南收束为选择性内容库工作流；
- `b4eb1f4`：再次明确视频只提供音轨，不提供观看界面。

**[F]** 当前产品路径大致为：

```text
自动恢复并扫描已配置来源
→ 首页内容集 / 待整理 / 开始发现
→ 扫描设备、选择文件夹或打开单个内容
→ 候选整理、收录或忽略
→ 选择首页显示的文件夹或播放列表
→ 建立队列并播放
→ 普通播放器
→ 有字幕或无字幕微光
```

### 3.4 演变对照

| 维度 | M0B 早期原型 | M1 单会话版本 | 当前版本 |
| --- | --- | --- | --- |
| 第一产品对象 | 正在发生的字幕 | 可恢复的媒体/字幕会话 | 已收录媒体与内容集 |
| 首页主动作 | 继续微光、打开新媒体 | 继续上次、新建播放 | 打开内容集、搜索、管理、迷你播放器 |
| 新内容入口 | 单次打开 | 独立选择媒体与字幕 | 设备扫描、文件夹、单文件 |
| 字幕地位 | 主内容、双语、可切显示 | 独立来源、播放器视觉中心 | 可选关联与状态标签 |
| 微光门槛 | 围绕字幕成立 | 有字幕才有有意义的阅读体验 | 无字幕也被定义为完整微光能力 |
| 长期组织 | 无 | 一个最后会话 | 文件夹、播放列表、队列、收录/忽略 |
| 用户维护成本 | 很低 | 低 | 中到高，取决于扫描规模 |
| 主要产品风险 | 内容来源不足 | 单会话过轻 | 变成通用本地播放器、独特价值后置 |

### 3.5 对演变的初步判断

- **[I]** 当前新增能力不是无价值的。它们解决了后台可靠性、内容恢复、隐私、错误匹配、队列和再次使用等真实问题。
- **[I]** 问题更可能不是“资源库做错了”，而是它从支撑层上升成了首要产品表面。
- **[I]** 早期版本的惊艳感可能来自极强的注意力聚焦：一份内容、一个时间源、一组同步文字、一个明确的退场动作。当前版本在用户看到这一结果之前增加了较多整理和播放器决策。
- **[H]** 把资源库降为可选能力，同时保留其可靠索引和关联基础，可能比删除资源库或继续扩充资源库更合理。

## 4. 当前实现的事实盘点

### 4.1 当前内容发现入口

**[F]** 当前支持三类来源：

1. **系统媒体库**：通过 MediaStore 扫描获得授权的音频和视频；
2. **授权文件夹**：通过 Storage Access Framework 的目录授权递归扫描媒体与外挂字幕；
3. **单独打开**：通过系统文件选择器打开一个媒体，并记住为已收录内容。

**[F]** 首次空库界面把“扫描本机”作为第一项强调操作，之后才是“选择文件夹”和“打开单个文件”。这是一项当前信息架构选择，不代表用户已经证明更偏好扫描。

**[F]** 应用冷启动恢复配置后会重新扫描已经配置的系统来源与全部授权文件夹；扫描结果再按用户决策分为已收录、待整理和已忽略。当前不是增量索引：文件夹媒体会在每轮扫描中逐项读取媒体元数据。

- **[I]** 当授权范围很小时，这种行为简单可靠；当用户授权大型目录或完整设备媒体库时，它会把启动等待、I/O 与候选维护成本一起放大。
- **[Q]** 如果资源库降为可选能力，扫描应该由启动自动触发、进入文件夹时按需触发，还是使用显式刷新与增量索引？

**[F]** 系统扫描和文件夹扫描采取同一候选逻辑：

- 新发现内容不会直接进入搜索、首页或播放队列；
- 音频候选默认预选；
- 视频候选默认不选；
- 用户可以收录、忽略和恢复；
- 首页只展示用户明确选择的文件夹或播放列表。

**[F]** 即使用户主动选择的是一个明确的小文件夹，当前仍要经过“扫描 → 待整理 → 选择媒体 → 收录 → 选择首页内容集”的管理流程。对全机扫描而言这套确认机制保护了隐私；对高意图的小目录而言，它是否构成不必要的使用税负仍待验证。

### 4.2 真机记录暴露出的规模问题

**[F]** [`../records/M2_SELECTIVE_LIBRARY_VALIDATION.md`](../records/M2_SELECTIVE_LIBRARY_VALIDATION.md) 的测试设备一次系统扫描发现：

- 95 项音频；
- 158 项视频；
- 总计 253 项候选；
- 最终用户只选择一个含 7 项音频的文件夹作为首页内容集。

选择性收录成功避免了 158 个视频自动进入首页，这是隐私与信任上的成功；同一记录也说明，广泛扫描可能产生远大于当前意图的候选集合。

- **[I]** “能够安全处理大量扫描结果”和“用户愿意先大量扫描”是两个不同命题。
- **[Q]** 对第一核心用户而言，系统媒体扫描究竟是常用入口、低频补充，还是不应主动呈现的高级功能？

### 4.3 当前外挂字幕发现

**[F]** 当前自动字幕发现只发生在获得目录权限的文件夹扫描中：

- 递归发现 SRT、LRC、WebVTT、ASS 和 SSA；
- 只匹配同目录候选；
- 媒体与字幕主文件名完全相同，或字幕文件名以 `媒体主文件名.` 开头时视为候选；
- 因此 `movie.mp4` 可以匹配 `movie.srt`、`movie.zh.srt` 等；
- 多个候选存在时，目前选择文件名主干最短的一个；
- 用户收录媒体时，建议关系才进入持久化关联。

**[F]** 当前应用的 MediaStore 系统扫描代码只查询音频和视频，不查询字幕条目，也不会沿媒体条目寻找同目录外挂字幕。因此在当前实现中，“扫描全机”和“自动建立外挂字幕关系”是断开的两条路径。

**[E]** 这不是 Android 平台的绝对限制。Android 11 / API 30 起，`MediaStore.Files.FileColumns` 定义了 `MEDIA_TYPE_SUBTITLE`，可表示字幕或歌词文件；它可能成为系统本地文件发现的一条优化路径。但其覆盖取决于系统索引、设备实现、Android 版本和文档提供者，不能替代用户授权文件夹或手动选择，也不能保证获得可靠的媒体父目录关系。

**[F]** 待整理列表仅用“匹配字幕”标记表示建议，已收录内容和曲目行仅用“字幕”标记表示已有关系。当前没有独立的字幕候选列表、语言标记、内容预览、置信度解释或多轨切换入口。

**[F]** 自动匹配只为每个媒体保留一个候选；当前不会把其他候选继续暴露给用户确认，也不会保存“为什么选择它”的匹配依据。

**[F]** 建议字幕只会在媒体从“待整理”进入“已收录”时被复制为正式关联。某个媒体已经收录后，用户后来把同名字幕放入授权文件夹，再次扫描可以产生新建议，但当前不会自动把它晋升为该媒体的正式字幕关系。

**[F]** M2 真机验收没有准备带同名字幕的 SAF 文件夹，因此当前自动匹配逻辑已有代码和单元级结构，但尚无专项真机样本记录。

### 4.4 当前单文件与字幕配对

**[F]** “打开单个内容”仍保留了早期会话模型的一部分：

- 播放内容与同步字幕是两个独立槽位；
- 允许只选媒体、只换字幕、移除字幕；
- 支持 SRT、LRC、VTT 和 ASS；
- 字幕读取成功后显示 cue 数量；
- 媒体与字幕在用户点击“开始播放/应用并播放”时建立关联。

**[F]** 单文件授权本身不提供可靠的父目录枚举权，因此当前不会在打开媒体后自动查看旁边的字幕。用户必须：

1. 再次打开字幕文件选择器；或
2. 改为授权整个文件夹，让应用扫描同目录候选。

- **[I]** 这条单文件路径在能力上接近早期产品，但在当前首页中被放在“发现内容”和管理层级之下，也没有被表达为最快进入微光的主路径。
- **[Q]** 产品是否应该把“打开媒体 + 选择字幕”重新提升为一级任务，并在需要自动发现时邀请用户授权当前文件夹？

### 4.5 当前字幕与队列联动

**[F]** 字幕关联以 `mediaUri → 一个 SubtitleSourceRef` 保存。

**[F]** 从资源库开始播放或队列切换媒体时：

- 应用先建立新的活动媒体会话；
- 若活动会话没有字幕，再异步读取该媒体保存的字幕关联；
- 读取成功后更新当前会话、草稿和恢复快照；
- 手动为当前媒体选择字幕后，也会更新对应关联。

**[F]** 自动关联字幕读取失败时，当前流程不会在播放器表面解释失败原因或提供替换动作，而是继续保持无字幕状态。冷启动恢复字幕失败也会以相同方式退回无字幕。

这说明当前已经存在基础的“逐媒体字幕记忆”，但产品表面仍然把它表现为附件状态，而不是组织和发现能力。

**[F]** 普通播放器只在当前没有字幕时提供“添加字幕”入口；已有字幕时，没有在播放现场直接查看来源、更换、切换或移除字幕轨的入口。手动替换仍需回到 Home 的单文件会话草稿。

### 4.6 当前字幕文档能力

**[F]** 当前 `SubtitleCue` 只包含：

```text
startMs + endMs + text
```

**[F]** 同一时间范围的多行 ASS Dialogue 或同一时间的多条 LRC 会被合并成换行文本。当前没有结构化保存：

- 原文与译文角色；
- 语言代码；
- 主轨与次轨；
- 多个可切换字幕来源；
- 外挂、内嵌字幕和标签歌词的来源类型；
- 字幕质量、置信度或匹配依据。

**[I]** 因此早期原型中的 primary / secondary 双语联动，在当前实现中只能作为不可区分的多行文字近似，无法独立控制显示、样式或语言。

### 4.7 当前尚未进入产品表面的字幕来源

**[F]** 当前未正式接入：

- MKV、MP4、WebM 等容器中的内嵌定时字幕轨；
- FLAC、Ogg 等标签中的同步歌词或普通歌词；
- Android 平台或第三方歌词服务；
- 在线字幕搜索；
- ASR 生成字幕；
- TransVortex 项目自动导入。

这些来源不应一次全部进入范围，但研究必须判断它们对首要用户的覆盖价值和合理顺序。

### 4.8 当前普通播放器与微光

**[F]** 普通播放器仍保留上一句、当前句、下一句字幕语境，以及进度、上下项、快退快进、倍速、偏移、队列、循环、随机和睡眠定时。

**[F]** 当前没有字幕时会显示“当前会话没有字幕”，但仍突出“无字幕 · 进入微光”。无字幕微光持续显示纯黑，只在手势或临时控制时点亮操作信息。

**[F]** 当前 cue 切换没有专门的字幕过渡、逐词/逐行进度、完整可滚动 transcript、可点按上下文跳转、手动浏览后“回到当前句”或语言层级；动画主要用于手势反馈和临时控制显示。

**[F]** 当前恢复保存会话和从首页点击继续都会进入 Normal Player；应用没有保存“上次是否处于 Glow”的表面状态，因此早期原型中的“一步继续微光”已经不在当前路径中。

- **[I]** “无字幕也能进入微光”是播放完整性能力，但它弱化了字幕作为产品身份的约束。
- **[Q]** 无字幕微光应该继续作为正常能力存在，但是否应退出首要叙事与主按钮文案？

## 5. 当前版本值得保留的产品资产

研究不应把“回到早期版本”理解为机械回滚。当前版本已经形成以下重要资产：

### 5.1 播放可靠性

- 后台 MediaSession 与系统媒体控制；
- 冷启动与进程恢复；
- 播放位置、倍速、字幕偏移、队列与模式保存；
- URI 失效后的重新定位；
- 睡眠定时；
- 音频和视频容器统一作为声音时间源。

### 5.2 内容信任边界

- 发现不等于收录；
- 视频默认不选；
- 忽略内容不会反复打扰；
- 文件不复制到应用目录；
- 目录授权、系统媒体和单文件来源可区分；
- 移除应用内来源或条目不会删除原文件。

### 5.3 字幕基础

- 四类主要外挂格式进入统一时间轴；
- 文件夹同目录保守匹配；
- 手动配对与逐媒体关联；
- 小型规范化字幕副本支持恢复；
- seek、倍速、暂停和队列切换仍以播放器时间为字幕真相。

### 5.4 微光基础

- 真正纯黑根表面；
- 窗口亮度、字幕像素亮度和控制亮度分离；
- 首次校准与预览；
- 沉浸系统栏控制；
- 锁定态与临时操作；
- 无字幕、字幕 gap 和错误状态不会用装饰填满屏幕。

**[I]** 下一阶段最有价值的工作可能是重新编排这些资产，而不是继续扩充能力清单。

## 6. 核心产品矛盾

### 6.1 字幕主角与字幕附件

早期产品把字幕定义成“今晚的内容”；当前领域关系仍是媒体条目拥有一个可选字幕附件。

- 如果字幕只是附件，产品会自然向本地音乐播放器靠拢；
- 如果字幕是主内容，内容发现、首页、播放器、历史和文件夹都应显式表达字幕状态；
- 但字幕又不能成为播放硬门槛，否则没有字幕的媒体和未来字幕生成路径会变得僵硬。

**[Q]** 怎样实现“字幕优先，但字幕不强制”？

### 6.2 立即使用与长期整理

用户的即时任务可能是“今晚打开这一集”，而不是“建立完整资料库”。

- 单文件最直接，但无法自动枚举旁边字幕；
- 文件夹能可靠发现媒体与字幕，但可能递归出很多无关内容；
- 系统媒体库覆盖广，但最容易混入音乐、录音、相册视频和社交应用缓存；
- 长期资源库适合复用，却把第一次价值推迟到整理以后。

**[Q]** 产品默认应该服务“一次明确播放意图”，还是“长期建立可回访内容集”？二者如何分层而不互相阻塞？

### 6.3 音乐库范式与字幕阅读范式

当前资源库拥有文件夹、播放列表、队列、随机和循环等音乐播放器概念。它们对播放可靠性有价值，但无法自动产生字幕联动。

歌词/字幕产品更关心：

- 当前内容是否有同步文字；
- 有哪些语言或版本；
- 是否自动匹配正确；
- 当前读到哪一句；
- 能否从某一句继续或重听；
- 原文与译文怎样呈现；
- 下一项是否也具备可读字幕。

**[Q]** 首页和列表是否应该支持“有字幕”“双语”“待匹配”“无字幕”等状态，而不是只按媒体元数据组织？

### 6.4 广泛发现与隐私/噪声

选择性收录解决了广泛扫描的后果，但没有回答扫描本身是否符合用户预期。

- 相册视频可能私密；
- 系统音频可能数量巨大且与夜读无关；
- 授权请求可能在用户理解价值之前发生；
- 候选整理把产品从消费工具变成维护工具；
- 另一方面，完全依赖单文件会削弱连续剧集、专辑或课程的复用。

**[H]** “用户主动授权的小文件夹”可能是隐私、自动字幕匹配和长期复用之间的最佳中间层。

### 6.5 自动匹配效率与错误成本

字幕自动匹配能显著降低摩擦，但错误字幕比没有自动字幕更糟。

研究需要定义至少三层置信度：

1. 高置信：同目录、完全同主文件名；
2. 中置信：语言后缀、版本后缀或可解释的剧集编号规则；
3. 低置信：模糊名称、相似时长或跨目录候选。

**[Q]** 哪些可以自动采用，哪些只能建议，哪些不应出现？多候选如何预览和记忆？

### 6.6 微光惊艳与日常留存

一小时正向体验说明核心表面有潜力，但产品是否成立还取决于：

- 用户是否愿意准备或寻找字幕；
- 第二天是否能快速继续；
- 是否优于普通播放器暗色模式或直接锁屏；
- 一小时后的舒适度是否能在不同设备和用户上重现；
- 惊艳感是否会变成稳定习惯，而不只是一次新奇体验。

**[Q]** 哪些进入前和退出后的体验，决定微光从 demo 变成日常产品？

## 7. 需要重新确认的核心用户与内容类型

研究不应假设“本地媒体用户”是一个统一群体。至少需要分别研究：

### 7.1 本地视频 + 外挂字幕用户

典型内容：下载的外语访谈、纪录片、课程、影视剧集、演讲。

- 字幕通常与视频同目录；
- 一集一个媒体文件，可能有多个语言字幕；
- 用户在夜间不想看画面，但理解内容需要文字；
- 文件夹和剧集编号可能比音乐标签更可靠。

这是目前最接近早期核心 JTBD 的候选首要用户，但仍需要与真实内容取得方式一起验证。

### 7.2 本地音乐 + LRC 用户

典型内容：本地歌曲、专辑、已有 LRC 歌词。

- 苹果音乐、Spotify 和本地音乐播放器已经建立同步歌词心智；
- 用户可能期待逐行、逐词、点按跳转和沉浸歌词；
- 媒体库、专辑和播放列表比视频用户更自然；
- 但荧荧若只复制歌词页，很难形成独立价值。

### 7.3 音频课程、播客和有声内容用户

- 长内容与继续播放需求强；
- 睡眠定时和长暂停恢复有价值；
- 手头往往没有现成定时字幕；
- 若用户喜欢微光但缺少字幕，ASR 才可能获得真实进入理由。

### 7.4 单次文件用户

典型场景：刚下载、刚收到、刚从其他应用导出的一个媒体文件与一个字幕文件。

- 不一定想建立长期资源库；
- 期待快速配对、播放和之后可继续；
- Android 单文件授权限制了自动查找同目录字幕；
- 产品需要解释“选择字幕”与“授权文件夹自动发现”的差别。

### 7.5 文件夹型长期用户

典型场景：一个课程、剧集、访谈系列或有声项目放在一个明确文件夹中。

- 文件夹本身已经是用户做过的组织；
- 可以一次建立多组媒体/字幕关系；
- 适合有限、可解释的扫描范围；
- 可能不需要全设备资源库、专辑或歌手分类。

### 7.6 无字幕的本地音频用户

- 当前播放器已经可以很好地服务这类用户；
- 但纯黑无字幕微光与直接锁屏相比，差异较弱；
- 除了应用内手势、防误触和快速恢复外，持续亮屏未必有明显收益。

**[Q]** 这类用户应该是兼容对象、次要用户，还是产品主线的一部分？

### 7.7 暂定非核心用户

除非研究找到反证，当前不应围绕以下用户设计主路径：

- 只想关屏听音乐、完全不需要同步文字的人；
- 需要完整视频观看表面的人；
- 主要依赖在线视频目录、推荐和社交的人；
- 必须由应用先生成字幕才能开始任何使用的人；
- 需要专业字幕编辑、单词卡或完整语言学习系统的人。

## 8. 待研究的基本产品对象

研究模型必须比较以下模型，不能默认沿用“媒体条目 + 可选字幕字段”。

### 模型 A：媒体条目

```text
MediaItem
└─ optional subtitle
```

优点：符合播放器和系统媒体库；容易建立队列。

风险：字幕天然退化为附件，难以表达多语言、多来源和阅读进度。

### 模型 B：播放/阅读会话

```text
Session
├─ media source
├─ zero or more timed-text sources
├─ active text selection
├─ playback position and subtitle offset
└─ display preferences
```

优点：最接近早期强体验和恢复需求。

风险：批量组织、队列和跨会话浏览需要额外结构。

### 模型 C：可播放阅读单元

```text
PlayableReadingUnit
├─ one media source
├─ discovered/selected timed-text tracks
├─ remembered language/layout choice
└─ progress and matching provenance
```

文件夹、播放列表和历史保存的是这种单元，而不是裸媒体。

优点：字幕成为一等能力，同时保留文件夹和队列。

风险：模型和界面概念可能比普通用户语言复杂，需要隐藏技术术语。

### 模型 D：文件夹/项目

```text
Folder or Project
└─ many media/subtitle pairs
```

优点：适合剧集、课程和用户已有目录结构；自动匹配范围清晰。

风险：单文件和系统媒体来源需要降级路径；深层目录可能过度扫描。

**[H]** 当前最值得验证的是模型 C 与模型 D 的组合：用户只看到“内容”和“文件夹”，内部保存媒体、字幕、语言、偏移和进度的完整关系。

## 9. 候选产品方向

研究至少应比较以下四个方向，并允许提出更好的第五种。

### 方向 1：单会话字幕夜读器

首页只保留继续和打开新内容。每次建立一个媒体/字幕会话，最多保存少量最近记录。

- 优点：价值最聚焦，首次体验短；
- 风险：连续剧集、批量字幕和长期复用较弱；
- 适合验证：微光体验本身是否足以成立。

### 方向 2：文件夹优先的夜间内容库

用户主动选择一个小范围文件夹，应用建立媒体/字幕配对，首页以这些文件夹和继续播放为主。

- 优点：自动字幕发现自然、隐私范围清楚、适合系列内容；
- 风险：Android 文件夹选择仍有摩擦，单次内容可能显得过重；
- 适合验证：用户真实文件组织是否足够稳定。

### 方向 3：会话优先、资源库可选

首页首先是继续、打开媒体、打开文件夹和最近会话；设备媒体扫描放在“更多来源”或用户主动建立资源库时出现。

- 优点：保留当前工程资产，同时让核心体验前置；
- 风险：两套入口可能造成概念重复；
- 适合验证：能否兼顾即时任务和长期复用。

### 方向 4：当前选择性资源库继续深化

保留设备扫描、候选整理、文件夹、播放列表和首页选择，在此基础上增加字幕筛选、配对和歌词式播放器。

- 优点：完整、可扩展，适合大量本地内容；
- 风险：维护成本高，独特体验晚，容易与成熟本地播放器正面竞争。

### 初步倾向

**[I]** 当前证据更支持优先研究方向 3，其次是方向 2：

```text
首页
├─ 继续上次那一句
├─ 打开一个媒体
├─ 打开一个文件夹
├─ 少量最近内容/文件夹
└─ 更多来源：可选设备媒体库
```

这是研究前的工作假设，不是预设结论。研究模型必须寻找反证。

## 10. 字幕发现与联动的完整问题空间

### 10.1 来源层

研究需要分别评估：

1. 用户手动选择的外挂字幕；
2. 授权文件夹内同目录外挂字幕；
3. 媒体容器内嵌字幕轨；
4. 音频标签中的同步歌词或普通歌词；
5. 未来本地或云端 ASR 生成字幕；
6. 未来 TransVortex 或其他工具导出的项目/字幕；
7. 在线字幕搜索或歌词服务，仅作为长期边界研究。

还应研究两类“入口”而不只研究字幕来源：

- 从文件管理器或下载应用通过“用荧荧打开”建立临时会话；
- 一次多选媒体与字幕，由用户显式把一小组文件交给荧荧。

### 10.2 发现层

对每种来源回答：

- 何时发现：导入时、播放时、用户请求时还是后台索引时？
- 发现范围：当前文件、当前文件夹、子目录、系统媒体库还是在线？
- 是否需要额外权限或网络？
- 能否得到语言、标题、格式、时长和来源信息？
- 多个候选怎样排序？
- 发现失败怎样恢复？

### 10.3 匹配层

至少研究：

- 完全同名；
- 语言后缀，如 `.zh`、`.en`、`.ja`；
- forced、SDH、CC、default 等常见后缀；
- 剧集季集编号；
- release/version 后缀；
- 媒体时长与字幕时间范围；
- 文件大小或哈希是否有价值；
- 模糊匹配的可解释性；
- 同一媒体多字幕、同一字幕误配多媒体；
- 字幕孤儿文件和媒体孤儿文件。

### 10.4 选择与预览层

字幕候选至少可能需要显示：

- 文件名或轨道名；
- 语言；
- 外挂/内嵌/歌词/生成来源；
- cue 数量与时间范围；
- 前几句安全预览；
- 匹配依据与置信度；
- 是否双语；
- 是否已在这个媒体上使用过。

研究需要判断哪些信息对普通用户有用，哪些只应进入诊断。

### 10.5 播放联动层

需要研究的体验包括：

- 切换队列项时自动恢复对应字幕；
- 没有字幕时是否提示寻找、选择或生成；
- 有多个语言时怎样快速切换；
- 原文、译文和双语布局；
- 点按某句跳转；
- 上一句/下一句与当前句的视觉层级；
- 逐行与逐词高亮是否有价值；
- 长句、字幕 gap、重叠 cue 和说话人信息；
- 暂停、seek、倍速和 offset 后如何重新建立阅读上下文；
- 从通知或系统恢复后怎样回到同一句。

### 10.6 记忆与恢复层

每个媒体/字幕关系可能需要保存：

- 上次选择的字幕；
- 手动选择是否覆盖自动匹配；
- 字幕偏移；
- 语言与单语/双语布局；
- 播放位置与当前 cue；
- 字幕失效后的重新定位信息；
- 用户拒绝过的错误候选；
- 文件移动后的关系恢复策略。

## 11. 竞品与相邻产品研究范围

研究不能只罗列功能。每个产品都要回答“它解决的任务是否与荧荧相同，以及它的设计为什么成立”。

### 11.1 同步歌词产品

至少研究当前版本的：

- Apple Music；
- Spotify；
- YouTube Music；
- Musixmatch；
- Poweramp、Musicolet、Symfonium 或一至两个仍活跃、重视本地歌词的 Android 音乐播放器。

重点不是音乐库外观，而是：

- 歌词入口的可发现性；
- 当前行、过去行和未来行的层级；
- 逐行/逐词同步；
- 点按跳转；
- 翻译或多语言；
- 无歌词状态；
- 歌词与队列、封面和完整播放器的关系；
- 为什么用户会停留在歌词页。

### 11.2 本地视频与字幕播放器

至少从以下类别选择有代表性的产品：

- VLC Android；
- mpv 及其 Android 前端；
- Just (Video) Player、Nova Video Player、Kodi、MX Player 或同类；
- Jellyfin 等媒体库产品，仅研究字幕轨和匹配，不照搬服务端架构。

重点研究：

- 外挂字幕自动发现规则；
- 多字幕轨选择；
- 内嵌字幕接入；
- Android 文件权限与文件夹访问；
- 字幕延迟和同步；
- 错配时怎样恢复；
- 文件夹浏览和媒体库扫描谁是主路径。

### 11.3 长内容与继续播放产品

研究 Apple Podcasts、YouTube transcript、Voice Audiobook Player、AntennaPod、Audiobookshelf 或其他长内容产品：

- 首页怎样突出继续；
- 进度如何跨长内容恢复；
- 文件夹是否等同一本书/一个项目；
- 睡眠定时如何进入主路径；
- 中断后怎样重新建立上下文。

### 11.4 阅读与提词产品

研究字幕阅读、teleprompter、沉浸阅读或辅助阅读产品：

- 文本字号、行距、位置和语言布局；
- 连续阅读时的眼动与上下文；
- 控制退场后怎样保持可恢复；
- 暗室使用和可访问性边界。

### 11.5 Android 平台约束

必须使用 Android 官方文档、Media3 官方文档和开源代码核对：

- `ACTION_OPEN_DOCUMENT` 与 `ACTION_OPEN_DOCUMENT_TREE` 的能力边界；
- Document Provider 是否允许可靠枚举父目录；
- MediaStore 音频、视频与字幕元数据可见范围；
- Android 14+ 部分媒体访问；
- Media3 内嵌字幕轨发现、选择和 cue 接入；
- 音频 metadata lyrics 的现实标准化程度；
- 分享/打开方式能否成为低摩擦入口。

### 11.6 零成本替代方案

研究必须把荧荧与用户已经拥有的替代方式比较，而不只与独立竞品比较：

- 普通播放器最低亮度与 AMOLED 黑色主题；
- 直接关闭屏幕只听；
- Android Live Caption 等系统能力；
- 视频播放器全屏只看字幕或遮住画面；
- 文件管理器直接用 VLC、mpv 或其他播放器打开；
- 将手机扣下、远离床位或使用耳机控制。

这些替代方案决定“单字幕发光”解决的是理解、光污染、控制、隐私还是情绪氛围，不能被略过。

### 11.7 已确认的初步模式证据

以下内容不是竞品结论，而是交给研究模型继续核对和解释的起点：

- **[E] Apple Music**：时间同步歌词位于 Now Playing 体验内，当前内容随播放推进，点按歌词行可跳转到对应位置；没有时间同步数据时可退化为完整静态歌词。这说明“当前行联动 + 点按定位 + 无同步降级”已经是成熟模式，但 Apple 的流媒体元数据、逐词动画和音乐消费场景不能直接套用到本地长字幕。
- **[E] mpv**：`--sub-auto` 默认采用较保守的 `exact` 匹配，更宽松的 `fuzzy` 和 `all` 需要显式选择。这支持“高置信度自动关联、低置信度只建议”的方向，不能据此假定某套文件名规则适合荧荧的所有内容。
- **[E] Kodi / Jellyfin**：成熟媒体系统普遍识别同名外挂字幕以及 `.en`、`.forced`、`.sdh` 等语言或角色后缀。字幕不是单个布尔属性，而可能是一组带语言、角色和来源的轨道。
- **[E] VLC Android**：字幕延迟校准使用“听到声音”和“看到文字”两个语义动作来计算偏移，提示同步修正可以围绕用户感知设计，而不必只暴露毫秒输入框。
- **[E] Android SAF**：单文件授权适合最小权限打开，但单个 `DocumentFile` 不能可靠枚举相邻内容；`getParentFile()` 只在用户已选择的 tree 内有定义。目录枚举需要用户明确授予 document tree。树授权覆盖所选目录及子目录，但大树遍历存在性能成本，Android 11 起也限制选择部分根目录。
- **[E] MediaStore**：API 30 起存在字幕/歌词媒体类型，值得验证它能否减少设备本地扫描成本；它不能覆盖未被系统索引、较旧系统、部分 OEM、云端文档提供者或 SAF 树中的全部内容，因此只能是发现层之一。
- **[E] Media3**：ExoPlayer 支持为媒体项配置外部字幕，独立字幕格式包括 WebVTT、TTML、SubRip 和 SSA/ASS；LRC 不在该独立字幕支持列表中，荧荧现有 LRC 解析仍属于自身能力。研究还要区分可解析文本字幕、图形字幕和音频标签歌词。

这些模式共同指向两个待验证的闭环，而不是一个“歌词页”功能：

1. **发现闭环**：用户如何知道某个内容有字幕、找到候选、理解匹配依据，并在错配时修复；
2. **联动闭环**：当前句如何跟随播放，用户如何查看上下文、点按跳转、校正偏移，并在手动滚动后回到当前句。

## 12. 研究问题清单

### 12.1 用户与场景

1. 哪类用户最常在关灯、宿舍、伴侣已睡或其他低光环境中继续消费需要文字理解的内容？
2. 他们使用的是本地视频、音乐、课程、播客、有声书还是其他内容？
3. 他们怎样获得这些内容和字幕？文件通常怎样组织？
4. “不想看画面但仍需文字理解”发生得多频繁、持续多久？
5. 他们当前用什么替代：播放器暗色模式、只听、锁屏、调低亮度、把手机扣下还是其他方式？
6. 哪个时刻会让他们认为荧荧不是一个 gimmick，而是值得保留的工具？

### 12.2 首次使用与回访

1. 首次体验是否应该提供内置样片，先证明微光价值，再请求任何文件或权限？
2. 用户愿意先选媒体还是先选文件夹？
3. 什么时候解释字幕匹配和文件夹授权最自然？
4. 用户是否接受第一次进入微光前校准？应多短？
5. 回访首页是否应该一键直接继续微光，还是先回普通播放器确认？
6. 最近会话、最近文件夹和完整资源库各需要多大权重？

### 12.3 内容库

1. 目标用户是否真的拥有值得建立全量索引的大型本地媒体库？
2. 系统媒体扫描在什么情况下创造价值，而不是制造候选清理？
3. 文件夹是否已经足够承担长期组织？
4. 播放列表、随机、循环和完整队列对第一核心用户的真实优先级是什么？
5. 首页显示内容集是帮助还是额外配置？
6. 是否应该有“带字幕内容”视图或过滤，而不是传统歌曲/专辑分类？
7. 单文件是否应该进入资源库，还是只进入最近会话，直到用户主动保存？

### 12.4 字幕发现

1. 真实文件中，同名、语言后缀、剧集编号各占多大比例？
2. 单文件选择后，用户更愿意再次选择字幕，还是授权所在文件夹？
3. 多字幕候选时，语言、预览和文件名哪个最有决策价值？
4. 自动采用错误字幕的可接受率是否接近零？
5. 内嵌字幕轨能覆盖多少本地视频场景？应该早于全设备扫描吗？
6. LRC 和音频标签歌词对目标用户的重要性如何？
7. 是否需要结构化保留原文/译文，而不是把两行合并成文本？

### 12.5 字幕播放器体验

1. 当前行之外，上一句、下一句是否应该常驻？
2. Apple Music 式当前行聚焦、过去/未来行弱化是否适合字幕，而不只是歌词？
3. 点按字幕跳转、一句重听、逐词高亮分别有多少价值？
4. 双语默认开还是单语默认？怎样控制发光面积？
5. 字幕 gap、长停顿和暂停时应显示什么？
6. 微光中应该保留哪些隐藏手势，哪些必须可见？
7. 普通播放器与微光之间应该是一种渐进退场，还是两个明显页面？

### 12.6 产品定位

1. “只让字幕发光”是否比“OLED 本地播放器”更容易被理解和记住？
2. 字幕可选是否应该只是一项兼容原则，而不是首要传播信息？
3. 如果用户喜欢体验但缺少字幕，ASR 是否应成为下一阶段，而不是继续扩资源库？
4. 如果用户更愿意直接锁屏听，产品还有什么不可替代价值？
5. 产品应如何描述低发光体验而不做未经证明的健康声明？

## 13. 研究证据标准

### 13.1 偏见防护

研究模型必须主动审计以下偏见：

1. **创作者效应**：创作者熟悉文件、字幕和操作，不代表首次用户；
2. **新奇效应**：一次惊艳不等于留存，但也不能因此忽略它；
3. **早期版本模糊**：未记录的参数不能被当作已知最佳设计；
4. **沉没成本**：资源库、队列和播放列表已经实现，不构成其继续占据首页的理由；
5. **Apple 锚定**：可以研究歌词交互语法，不能照搬在线目录、版权和短歌曲前提；
6. **播放器完整性偏见**：播放器常见功能不自动等于荧荧需求；
7. **字幕原教旨偏见**：历史定义也必须接受“直接锁屏足够”的反证；
8. **扫描解决主义**：平台允许访问不等于用户愿意授权和整理；
9. **文件组织偏见**：创作者的目录和命名可能比普通用户整齐；
10. **工程验证即产品验证**：真机通过只证明可运行；
11. **格式覆盖偏见**：支持多个 parser 不等于解决字幕取得与匹配；
12. **永久收录偏见**：一次夜间播放可能只需要临时会话；
13. **健康营销偏见**：低发光不能直接推出护眼；
14. **低估外部受益者**：宿舍室友或伴侣不被屏幕照亮，可能比使用者自身舒适更重要。

### 13.2 来源优先级

1. Android、Media3、Apple 等官方文档和帮助；
2. 开源项目官方手册、源码、issue 和发布记录；
3. 同行评审论文和标准；
4. 应用商店页面与开发者说明；
5. 用户评论、论坛、Reddit、社区和视频，只作为定性需求信号；
6. 二手媒体文章仅用于发现线索，不单独支撑技术结论。

### 13.3 时效性

- 明确研究日期；
- 核对竞品当前版本，而不是凭印象描述；
- 对快速变化的 Android 权限、Apple Music、Spotify 和 Media3 能力给出直接链接和页面日期；
- 旧资料如果仍有价值，说明它用于历史模式还是当前能力。

### 13.4 论证要求

- 每个重要结论注明事实、推断或假设；
- 对竞品功能给出直接来源，不引用搜索结果页；
- 对无法获得的市场份额、用户规模和转换率不做虚构估算；
- 主动寻找不需要荧荧、直接锁屏已经足够的用户证据；
- 不把用户说“很酷”视为留存证据；
- 不因当前已经实现资源库，就默认资源库必须留在主导航；
- 不因早期一小时体验惊艳，就默认所有用户都会有相同体验。

## 15. 建议验证假设与信号

以下是研究起点，阈值应由研究模型进一步校准。

### H1：微光字幕相对普通播放器和锁屏具有独立价值

观察：用户在真实暗室内容中主动选择微光，并认为理解内容与环境干扰都得到改善。

反证：多数目标用户更愿意直接锁屏听，或认为普通暗色字幕页已经足够。

### H2：目标用户拥有或愿意准备定时字幕

观察：体验后愿意导入自己的第二份内容，或已经有稳定的字幕来源。

反证：体验被认可，但绝大多数内容没有字幕，且用户不愿手动寻找或生成。

### H3：单文件/文件夹入口优于全设备扫描

观察：用户自然从明确文件或文件夹开始；较少需要整理无关候选；更理解授权范围。

反证：用户普遍期望安装后立即看到全库内容，并频繁跨文件夹搜索和建立播放列表。

### H4：继续上次是最高频回访任务

观察：第二晚用户首先寻找继续，并希望直接回到相同媒体、位置、字幕、语言和微光设置。

反证：用户更常寻找新内容或随机播放，继续入口不是主任务。

### H5：字幕联动比扩充播放器功能更影响产品价值

观察：自动发现、可信匹配、双语和句子级交互显著提高完成率与复用意愿。

反证：用户更关心封面、均衡器、完整音乐分类或视频画面，字幕只是偶尔打开的附件。

### H6：文件夹是适合的中间组织层

观察：用户已有按剧集、课程或项目整理的目录；一次授权能形成多组高置信配对。

反证：真实内容高度散乱、来自云 Provider 或应用私有目录，文件夹选择无法形成稳定关系。

## 16. 建议的近期产品实验

### 16.1 实验一：重现早期惊艳感

目的：验证正向体验来自字幕中心与微光本身，而不是个人偶然偏好。

实验开始前先补录创作者那次一小时体验的设备、版本或近似界面、媒体、字幕、单双语、亮度、距离、环境光、姿势和结束后的视觉感受；无法确认的项目明确标记未知。

对照：

1. 早期字幕中心原型；
2. 当前普通播放器 → 微光路径；
3. 普通播放器暗色字幕页；
4. 直接锁屏只听。

任务：使用同一段 20–30 分钟真实内容，完成播放、暂停、回退、恢复和退出。

记录：

- 进入目标状态的时间与动作数；
- 是否持续阅读；
- 理解感、环境干扰、主观舒适度；
- 是否误触或找不到控制；
- 结束后是否愿意导入自己的内容；
- 第二天首先想继续还是打开新内容。

### 16.2 实验二：内容入口比较

让参与者分别完成：

1. 打开一个媒体，再选字幕；
2. 选择一个包含多组媒体/字幕的文件夹；
3. 扫描设备媒体库并整理候选。

记录：

- 是否理解每种授权；
- 找到目标内容的时间；
- 无关候选数量；
- 自动匹配正确率；
- 对隐私和控制感的评价；
- 之后是否能再次找到同一内容。

### 16.3 实验三：字幕联动深度

依次验证：

- 当前句；
- 上一句 + 当前句 + 下一句；
- 原文 + 译文；
- 点按句子跳转；
- 一句重听；
- 逐词高亮。

不要默认功能越多越好。比较每项是否提高理解、恢复上下文和持续使用意愿，以及增加多少发光面积和操作复杂度。

### 16.4 七天重复使用研究

一次可用性测试无法区分惊艳与习惯。让目标用户使用自己的内容至少七天，记录：

- 第一天是否成功建立媒体/字幕关系；
- 第二次是否快速继续；
- 实际使用的是单文件、文件夹还是扫描；
- 有多少次因为没有字幕、错配或授权放弃；
- 是否继续停留在微光，还是逐渐改为直接锁屏；
- 是否主动添加第二份内容；
- 室友或伴侣是否注意到环境干扰变化。

## 17. Go / Rework / No-Go 判断框架

### Go

- 多名目标用户在自己的内容上主动偏好微光字幕；
- 第二次使用仍能快速继续；
- 至少单文件或文件夹路径能稳定建立字幕关系；
- 产品价值可以用一句非技术语言解释；
- 不依赖先建立完整资源库才能体验价值。

### Rework

- 用户喜欢微光，但导入和字幕匹配阻塞使用；
- 用户有内容但没有稳定字幕，需要重新评估内嵌字幕或 ASR；
- 用户喜欢文件夹，但当前资源库维护过重；
- 用户能理解产品，却无法快速恢复或控制播放。

### No-Go 或重新定位

- 目标用户在充分体验后仍普遍选择直接锁屏；
- 字幕阅读没有改善理解或体验，反而增加疲劳；
- 用户没有可获得的字幕，也不愿生成或寻找；
- 产品只有一次性视觉新奇，没有第二次使用意愿；
- 为了成立必须变成另一个完整音乐/视频播放器，且微光不再影响选择。

## 19. 当前工作假设，供研究反驳

在正式研究完成前，最连贯的暂定判断是：

> 荧荧首先是一款字幕优先的夜间听读产品。本地播放、文件夹和资源库是让字幕关系可靠、可恢复的支撑能力，不应把独特体验推迟到大范围扫描和整理之后。

对应的暂定产品骨架是：

```text
首次样片证明价值
        ↓
首页：继续 / 打开媒体 / 打开文件夹
        ↓
发现或选择字幕，确认可信关系
        ↓
字幕中心普通播放器
        ↓
只剩当前文字的微光

可选资源库：设备扫描、更多历史、播放列表
```

这不是结论。研究最重要的价值，是判断它是否经得起真实用户、真实文件结构、平台限制和现有替代方案的反驳。
