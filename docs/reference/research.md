# VortexCue / 荧荧 M0B–M1 产品与交互设计研究

> 原始报告：[ChatGPT 共享对话](https://chatgpt.com/share/6a754aca-d088-83e9-bffa-bf822748f8aa)

## 摘要

我先给结论：VortexCue / 荧荧在 M0B→M1 最有机会成立的形态，不是“极简本地播放器”，而是“以字幕为主内容、媒体只提供时间与声音的夜间阅读器”。 这一区别非常重要。只要 M1 开始围绕“播放器应该有什么”做加法，产品很快会变成一个功能较少的 VLC；如果围绕“怎样最快进入一段低干扰、可持续的字幕阅读”做设计，才有独立产品价值。

我下面用三种标记严格区分结论来源：

- **[F] 事实**：来自你提供的仓库文档、M0A 记录或当前一手资料。
- **[I] 推断**：基于这些事实得出的产品判断。
- **[H] 待验证假设**：值得进入 Compose/OLED 原型，但目前不应写成产品定论。

项目种子明确把 VortexCue 定义为 Android-first、Kotlin + Compose + Media3 的独立项目。 它原本的核心问题也是低光环境中“继续听媒体，同时阅读字幕”，而不是建立媒体库。

## 1. 核心用户与 JTBD

### 第一核心用户：已经拥有字幕的夜间媒体消费者

[I] 我建议 M1 首个真正核心人群收窄为：

已经有本地视频/音频和外挂 SRT，希望睡前、暗室、宿舍等环境继续听，并依靠字幕理解内容的人。

最典型的是：

- 外语视频 + SRT；
- 下载的访谈、纪录片、课程；
- 本地电影/剧集，但此刻并不想看画面；
- 有现成字幕的长访谈、讲座。

这个选择比“播客/有声书用户”更现实。

[F] 仓库目前同时把外语视频、播客、有声书、语言学习列为优先场景。

[I] 但 M1 明确不做 ASR，而大多数普通播客和有声书用户手中并没有对应 SRT。因此：

“播客/有声书”很适合 M0B 验证连续阅读舒适度，却未必是 M1 最容易自然获得内容的首批用户。

这是现有文档里一个很值得主动收紧的地方。

#### JTBD

当我晚上已经不想继续看明亮视频，但仍需要文字理解内容时，我希望声音继续播放，只留下当前需要阅读的一小段文字，让我不用在“关屏听不懂”和“亮着播放器看字幕”之间二选一。

### 第二核心用户：轻量语言学习者

不是 Lingopie 那种“学习工具用户”，而是：

我已经有字幕，只想在听的同时持续读原文/译文，不想点击单词、背卡片、看语法提示。

Lingopie 当前把双字幕、点击翻译、句子循环、慢速播放、词汇和语法工具做成完整学习系统。

[I] VortexCue 值得借的只有两件事：

- 双语字幕确实是稳定需求；
- 速度和一句重听对理解很有价值。

点击词典、flashcard、发音评分、侧边 transcript 都应该坚决留在 MVP 外。

### 第三用户：已有 transcript 的长内容听众

Voice Audiobook Player 的当前产品重点就是“准确回到上次位置”“控制就在手边”“除此之外尽量退场”。 AntennaPod 甚至会根据暂停时长自动往前回退几秒，让用户重新建立上下文。

[I] 这类产品给荧荧最有价值的启发不是“sleep timer”，而是：

连续性本身是一项产品能力。

对荧荧来说，“今晚打开以后 1–2 个动作回到昨天那一句”比媒体库、封面和分类重要得多。

## 2. 产品机会、矛盾和失败风险

| 类型         | 判断                                                                                        | 状态                                |
| ------------ | ------------------------------------------------------------------------------------------- | ----------------------------------- |
| 产品机会     | 普通 dark mode 仍然保持大量导航、按钮、卡片和文字；荧荧可以把“发光像素预算”提升成产品级约束 | [F/I]                               |
| 差异化       | 真正差异不是 `#000000`，而是“工作层 → 内容层 → UI 消失”的完整转换                           | [I]                                 |
| 最大验证风险 | 用户也许最终发现“直接关屏听”已经够了，并不愿持续读字幕                                      | [F] 这也是项目种子的 No-Go 条件之一 |
| 内容矛盾     | M1 不做 ASR，但播客/有声书通常没有 SRT                                                      | [I]                                 |
| 文件矛盾     | 想自动寻找同目录 SRT，但 SAF 单文件授权并不等于获得整个父目录                               | [F]                                 |
| IA 风险      | 每次打开都经过准备页，会让可靠性页面变成启动税                                              | [I]                                 |
| 手势风险     | 为了“UI 消失”设计过多隐藏手势，会让产品变成谜题                                             | [I]                                 |
| OLED 风险    | 低亮度并不等于无残影/烧屏风险，也不等于低功耗硬件模式                                       | [F]                                 |
| 无障碍矛盾   | 微光模式主动降低亮度，而标准可访问界面要求足够可读、足够大的控制                            | [F/I]                               |
| 品类风险     | 普通播放器功能一旦持续增加，核心会被 VLC/mpv 吞没                                           | [I]                                 |

其中 SAF 是一个现在就值得修改产品文档的地方。

Android 官方明确说，单个 DocumentFile 没有可靠的父路径概念，一个 document 甚至可以出现在多个目录中；官方也建议只需要一个文件时使用 ACTION_OPEN_DOCUMENT，真正需要整个目录才申请 ACTION_OPEN_DOCUMENT_TREE。

所以：

[I] 不应把“自动扫描媒体旁边的 SRT”当 M1 基础承诺。

合理模型应该是：

有候选集合时智能匹配；没有目录访问权时，老老实实让用户选择 SRT。

而且 Android 允许第二次打开系统 picker 时用 EXTRA_INITIAL_URI 提供初始位置，能降低第二次选择的成本。

## 3. 竞品模式：什么值得借，什么应该避免

### VLC：学习“能力的可恢复性”，不要学习它的手势密度

VLC Android 当前支持：

- 首次播放手势教学；
- 横滑 seek；
- 左/右竖滑亮度/音量；
- 外挂字幕选择；
- 字幕 delay；
- 以固定步长调整字幕同步；
- 甚至有“VOICE HEARD / TEXT SEEN”这种人工同步校准。

借：

- 字幕来源永远可以更换；
- offset 是一等播放状态；
- seek 后立即重新求字幕；
- 隐藏能力必须有明确入口。

不要借：

左滑右滑上下滑长按双击全部成为核心。
荧荧不是播放器高手工具。

### mpv：借它对字幕匹配的保守态度

mpv 的 --sub-auto 默认就是 exact：文件名相同、允许语言后缀；fuzzy 和 all 是更激进的显式选项。

这几乎可以直接转成荧荧的产品原则：

[I]

- movie.mp4 + movie.srt → 高置信；
- movie.mp4 + movie.ja.srt → 高置信；
- movie-final.mp4 + movie-cn-new.srt → 只能建议；
- 多个 fuzzy candidate → 必须让用户确认；
- 永远不要静默 fuzzy 配对。

因为错字幕比“没自动匹配”严重得多。

### Voice Audiobook Player：借“继续”，别借媒体库

Voice 当前宣传的核心之一就是保存每本书的位置并直接继续。

[I] 荧荧首页真正应该学习的是：

“上次我读到哪里”比“我拥有什么内容”重要。

因此首页的主对象应该叫继续，而不是“媒体库”。

### AntennaPod：借中断恢复思想

AntennaPod 会在暂停超过 1 分钟后回退 3 秒、更长暂停回退更多。

[H] 荧荧可以实验：

长暂停后恢复时自动回退 2–3 秒。

但我不建议直接放入 M1 默认行为。字幕时间精确的用户可能认为这是“播放器自己乱跳”。

### YouTube：已经教育好了用户的两个手势

YouTube Android：

- 轻点播放器 → 显示操作；
- 左右双击 → ±10 秒。

Android 官方沉浸式设计同样指出，沉浸内容中用户应该能够重新显示系统/UI，并且不要把交互目标放在系统手势区域。

所以这里我会明确挑战当前文档里的二选一：

[I] 单击应该默认“显示/隐藏控制”，而不是“播放/暂停”。

这比 A/B 两者等价更强。

### Teleprompter：借“阅读环境可调”，不要借滚动

Teleprompter.com 把字体、文字位置、速度等调整放在开始前和运行过程中都可访问。

荧荧可以借：

- 阅读参数是一级能力；
- 正在使用时仍能快速调整；
- 阅读表面本身尽量退场。

不要借连续滚动。SRT 的 cue 边界已经是时间语义。

### Android Reading Mode / W3C：阅读样式不是装饰设置

Android Reading Mode 允许修改颜色、字体、字号、粗体和行距。 W3C 的 caption requirements 也明确强调字幕以媒体为时间源、允许空白 cue、允许用户控制字体/颜色，并指出屏幕同时出现超过两种语言通常就不现实了。

[I] 这支持现有方向：

- 字号；
- 字重；
- 行距；
- 单语 / 双语；
- 位置；
- 颜色/灰阶；

都比播放器的“封面、队列、收藏”更接近产品本体。

## 4. 三套不同产品概念

### 概念 A：继续阅读型

核心精神：

打开荧荧，就是继续昨晚那段内容。

首页：

继续 → 播放 → 微光。

新内容才走导入。

优势：

- 最符合长时间媒体消费；
- 复用频率高；
- “两步进入微光”自然成立；
- 首页不需要媒体库。

代价：

- 首次使用很空；
- 对恢复正确性要求极高；
- URI、字幕、position、offset 都必须可靠保存。

推荐：M1 主模型。

### 概念 B：字幕准备台型

每次进入都先确认：

```text
媒体 ✓
字幕 ✓
同步 +0.2s
显示：双语 / 24sp / 暖灰
→ 开始
```

优势：

- 文件错误暴露得早；
- 适合复杂本地媒体；
- 调试和测试很舒服。

问题：

- 对熟练用户很烦；
- 正确内容也要反复确认；
- 很容易逐渐长成“项目设置页”。

推荐：变成异常/首次导入状态，而不是主流程。

### 概念 C：夜间会话型

产品启动更像一个仪式：

```text
夜深了，世界安静下来。
继续昨晚 / 开始一段微光阅读
```

进入后尽量不再离开阅读层。

优势：

- 品牌感最强；
- 非常适合 M0B；
- 最容易让用户感受到“它不是播放器”。

问题：

- 仪式每天重复就会拖沓；
- 很容易被体验者评价为“漂亮的 demo”；
- 不利于处理本地文件错误。

推荐：M0B onboarding 使用，不做 M1 主 IA。

### 最终建议

不是三选一，而是：

A 做骨架，B 做条件式恢复层，C 做首次体验。

这是我认为目前最稳的组合。

## 5. 推荐的信息架构与关键状态流

仍然赞成无底部导航。

```text
App
├─ 首页 Home
│ ├─ 继续上次
│ ├─ 打开本地媒体
│ ├─ 最近 3~5 条
│ └─ 设置 / 校准
│
├─ Ready Resolver
│ ├─ 已就绪
│ ├─ 缺少字幕
│ ├─ 字幕候选不确定
│ ├─ 字幕解析失败
│ └─ URI 授权失效
│
├─ 普通播放器 Normal Player
│ ├─ 字幕上下文
│ ├─ 播放定位
│ ├─ 字幕偏移
│ ├─ 显示设置
│ └─ 进入微光
│
└─ 微光播放器 Glow
   ├─ Controls Hidden
   └─ Controls Visible
```

最大的修改是：

准备页从“固定页面”降级成“Ready Resolver 状态”。

### 新媒体

```text
新媒体
打开媒体
↓
系统文件选择器
↓
媒体可读
↓
有没有已经可信的 SRT？
├─ 是 → Ready
└─ 否 → 选择 SRT
↓
解析 / 校验
↓
┌───────┴────────┐
↓ ↓
Ready Recoverable Error
↓
普通播放
↓
进入微光
```

### 继续上次

```text
继续上次
点击“继续”
↓
媒体 URI 仍有效？
↓
字幕 URI 仍有效？
↓
恢复 position + offset + display preset
↓
直接恢复播放表面
```

[I] “继续”不应该再次出现准备页。

如果上次就在微光里，可以直接恢复到微光；用户点“继续”本身已经是明确操作，不属于偷偷自动播放。

## 6. 四个关键页面怎么设计

### 首页

首页不是内容发现页，而是任务恢复页。

建议顺序：

- 继续；
- 打开本地媒体；
- 最近 3–5 个 session；
- 设置。

继续卡片保留：

- 标题；
- 32:14 / 1:20:03；
- SRT · 双语；
- “继续”。

#### 一个我会修改的地方

现有草图把“上一句字幕文本”放进首页卡片。

[H] 它有助于记忆定位，但也可能在桌面截图、旁人视线中泄漏用户正在看的内容。

我建议 M1 默认只显示：

文件名 + 进度 + 字幕状态

字幕 snippet 先不默认显示。

### 准备页 / Ready 状态

核心问题不应该是“让我确认所有配置”。

而应该是：

现在有什么阻止你放心播放？

例如：

```text
城市漫步访谈

媒体
interview.mp4
1:20:03 · 仅播放音轨

字幕
✓ interview.zh.srt
文件名匹配

预览
00:18 今晚我们想聊……
00:22 The first thing...

字幕偏移 +0.0s

[开始播放]
```

如果已经完全可信：

[I] 不一定需要完整页面，甚至可以是普通播放器顶部一条短暂状态：

已加载 interview.zh.srt · 更改

完整 Ready 页只在：

- 第一次；
- 多个字幕；
- 缺字幕；
- 字幕异常；
- 重新定位文件；

时出现。

### 普通播放器

这里我赞成现有文档的核心判断：

普通播放器也应该是字幕播放器，而不是视频播放器。

M1 不创建视频 Surface。

布局层次：

当前 cue

最大。

上一句 / 下一句

低对比、只在普通模式展示。

这两个 context cue 非常有价值，因为用户可以迅速判断：

- SRT 是不是选错；
- 时间是不是偏了；
- 双语是不是搞反；
- 当前内容在哪里。

下面才是：

- 时间；
- scrubber；
- -10s；
- play/pause；
- +10s；
- 倍速；
- 字幕偏移；
- 字幕设置。

最后一个视觉优先级最高的 CTA：

进入微光

### 微光播放器

隐藏状态：

黑底 + 当前字幕。

仅此而已。

[I] 不建议：

- 进度条常驻；
- 锁图标常驻；
- 微小 logo 常驻；
- “正在播放”点常驻；
- 时间常驻；
- gesture hint 常驻。

字幕空档时真正变黑，而不是保留上一句。这也符合字幕时间模型允许“此时没有 active cue”的基本语义。

#### 控制显示时

可以短暂增加：

```text
             当前字幕

       -10s    暂停    +10s

      32:14 ━━━━━━━ 1:20:03

     字幕 +0.2s   1.0×   退出微光
```

这里一个重要设计原则：

[I] 控制可以短暂比字幕亮。

“只让字幕发光”约束的是持续状态，不应该逼得用户连退出按钮都看不清。

但不要为了控制层突然提高整个 window brightness——那会形成明显亮度跳变。

控制文字/图标可用更高灰阶，窗口亮度保持不动。

## 7. 手势、可见控制和无障碍

我推荐 M1 先冻结成非常少的一组：

| 操作             | 默认行为                  |
| ---------------- | ------------------------- |
| 单击屏幕         | 显示 / 隐藏控制           |
| 双击左侧安全区域 | -10 秒                    |
| 双击右侧安全区域 | +10 秒                    |
| 系统 Back        | 退出微光 → 普通播放器     |
| 音量键           | 媒体音量                  |
| 耳机 / 蓝牙键    | Android MediaSession 行为 |

### 暂时不要做

- 上下滑调亮度；
- 上下滑改字号；
- 水平拖动任意 seek；
- 底部上滑打开控制；
- 中央单击暂停；
- 多指 gesture。

Android 官方明确要求避免把拖动/点击目标放到系统 gesture inset 中。

所以现文档里的：

“从底部安全区域上滑打开完整控制”

我建议从 M1 候选里直接降级。

### 为什么单击不是暂停

因为用户单击屏幕可能只是想：

- 看时间；
- 看当前偏移；
- 调速度；
- 退出；
- 确认播放状态。

如果单击同时会暂停，查看状态变成修改状态。

YouTube/沉浸播放器长期建立的“tap reveals controls”心智模型反而更安全。

### 无障碍

[F] Android 当前仍建议所有可交互触控目标至少 48dp × 48dp，Compose Material 组件自带很多 semantics，但自定义控件需要自行保证。

因此：

- 每个手势必须有按钮；
- Glow controls 本身至少 48dp target；
- -10s、暂停、+10s 有明确 semantics；
- 不用颜色单独表达“字幕已就绪”；
- 系统字体缩放生效；
- 自定义微光字号仍可单独放大；
- TalkBack 下完整核心操作必须通过 controls 完成。

[I] Touch Exploration 开启时，不应该让全屏 invisible gesture layer 抢夺正常探索逻辑。

另外必须接受一个事实：

微光模式的“极低亮度”本身不能和普通页面使用同一套可读性标准。

正确做法不是强行声称 Glow accessible，而是：

- 工作层保持标准可访问性；
- Glow 的亮度是用户主动选择；
- 提供“高可读”微光 preset；
- 用户可把字幕亮度/字号提高。

## 8. OLED 低亮度、残影和长期使用约束

这里我认为现有文档有一点需要收敛。

Google 对 Pixel OLED 的公开建议仍明确指出：同一个画面长时间、高亮度停留，会增加 burn-in 风险；降低亮度和减少静态显示时间有帮助。

你的 M0A 已经证明：

在一台 Vivo OLED 上，黑背景视觉消失 + 极低灰文字可读。

但它没有证明：

- 多设备亮度一致；
- 黑位/灰阶曲线一致；
- PWM 舒适；
- 功耗；
- 一小时舒适度；
- 残影；
- 长期烧屏安全。

这和项目种子记录的风险是一致的。

### 我建议 M1 默认采用的保护

#### 1. cue 结束就消失

不要延长上一句。

#### 2. 播放结束立即清字幕

最后一句不能变成永久静态文字。

#### 3. 暂停保护

[H] 参数仍待验证。

可以原型比较：

- A：30 秒变暗、120 秒隐藏；
- B：60 秒变暗、180 秒隐藏。

而不是现在就把 30 秒、2–5 分钟写成正式值。

#### 4. 控制层快速消失

2–4 秒是合理实验范围，但也是 [H]。

#### 5. 不显示静态 clock / logo / progress

这些反而比字幕内容更危险，因为字幕一直在变化。

### 我反而不建议 M1 默认做的东西：周期性移动字幕

现文档提出：

每 5–10 分钟换几个垂直位置。

理论上能分散固定区域。

但：

[I] 对这个产品而言，它可能引入一个比烧屏更直接的问题：阅读视线反复重新寻找文字。

而且我们没有证据说明：

- 5 分钟好；
- 10 分钟好；
- 移多少好；
- 用户是否察觉；
- 实际风险降低多少。

我的建议是：

把 position shift 保留成 OLED 实验开关，而不是 M1 默认保护。

第一层保护先依赖：

- 没有常驻 UI；
- cue 自然变化；
- 字幕 gap 纯黑；
- pause timeout；
- media-end cleanup。

### 系统 Extra Dim 也是一个干扰变量

Android 当前的 Extra Dim 可以把屏幕压到系统通常最低亮度以下。

所以 Window brightness + RGB grayscale 并不是最终面板亮度的唯一决定因素。

[I] 荧荧不应该尝试偷偷关闭：

- 自动亮度；
- Extra Dim；
- 护眼；
- 色彩校正。

应该在校准记录中告诉用户：

当前设备显示设置发生变化时，建议重新校准。

## 9. 我建议冻结的 MVP 范围

### M0B

只回答：

听真实媒体时，“字幕单独发光”是不是一种值得重复使用的体验？

包含：

- 3–5 分钟合法内置音频；
- 同步字幕；
- 普通播放；
- Glow；
- 播放 / 暂停；
- -10 秒；
- 字幕同步；
- 现有亮度校准；
- 一次非常短的首次手势提示。

不包含：

- SAF；
- MediaSessionService；
- 后台播放；
- 最近记录；
- SRT 选择；
- 账号；
- ASR。

### M1

只建立：

```text
打开本地音频 / 视频
→ 选择 SRT
→ 字幕解析
→ 普通播放
→ 调整 offset
→ Glow
→ 后台 / 锁屏媒体控制
→ 再次打开继续
```

技术上：

- Media3 ExoPlayer；
- MediaSessionService；
- SAF；
- SRT；
- SubtitleTimeline；
- position / offset；
- persistable URI；
- 一个 Last/Recent Session 模型；
- DataStore 级别的轻量持久化即可。

Android 官方目前仍推荐把后台播放器和 MediaSession 放入 MediaSessionService，系统媒体控制和耳机等外部 client 都可以直接连接 session。

### 明确非目标

M1 不做：

- LRC；
- ASS / WebVTT；
- 内嵌字幕；
- 视频画面；
- FFmpeg；
- 媒体扫描；
- 完整媒体库；
- 账号；
- ASR；
- 翻译；
- 字幕编辑；
- 单词学习；
- 在线字幕搜索；
- TransVortex 配对；
- .vtxsub；
- 收藏 / 队列 / 推荐 / 社交。

种子里长期支持 LRC、云端、项目格式等并没有错，但应该继续服从当前 ROADMAP，而不是反过来扩张 MVP。

## 10. 可执行 Compose 原型 + OLED 真机测试计划

### M0B：先做“体验闭环”，不要提前做播放器架构

我会直接在当前 app 上加入：

```text
MainActivity
├─ SampleIntro
├─ NormalSamplePlayer
└─ GlowPlayer
   ├─ Hidden
   └─ ControlsVisible
```

加入 Media3 ExoPlayer，但：

M0B 不上 MediaSessionService。

理由：它需要真实 player time，但不需要后台生命周期。

数据模型只要：

```kotlin
data class SubtitleCue(
    val startMs: Long,
    val endMs: Long,
    val primary: String,
    val secondary: String? = null,
)

data class DisplayCalibration(
    val windowBrightness: Float,
    val subtitleLevel: Int,
)
```

当前 cue：

```text
Player.currentPosition +
subtitleOffset
↓
SubtitleTimeline
↓
CurrentCue
```

绝不能有自己的“字幕计时器”。

这和现有 seed “媒体位置是真相”的原则一致。

### M0B 要测试的不是“喜不喜欢 UI”

任务脚本固定成：

- 启动；
- 开始样片；
- 进入微光；
- 阅读 30–60 秒；
- 找到暂停；
- 恢复；
- 快退 10 秒；
- 再次跟上字幕；
- 打开控制；
- 退出微光。

记录：

- 有没有问“怎么暂停”；
- 有没有误暂停；
- 是否找得到退出；
- 是否下意识想关屏；
- 是否觉得字幕太亮/太暗；
- 是否想继续读；
- 完成后是否愿意拿自己的内容再试。

现 ROADMAP 要求至少三次完整暗室记录。这是可以保留的最低门槛；为了做产品决策，我会倾向 5–8 名不同体验者，而不是同一开发者重复三次。

后一个数字是 [H] 研究建议，不是现有验收事实。

### M1 Compose 结构

等 M0B 过门再加入：

```text
PlaybackService : MediaSessionService
└─ ExoPlayer

MainActivity
└─ MediaController
└─ PlaybackUiState

SubtitleRepository
├─ SrtParser
├─ SubtitleTimeline
└─ CurrentCueResolver

SessionStore
├─ mediaUri
├─ subtitleUri
├─ positionMs
├─ subtitleOffsetMs
└─ displayPreset
```

不需要：

- DI framework；
- Room；
- 多 module。

### 文件路径

```text
ACTION_OPEN_DOCUMENT(media)
↓
takePersistableUriPermission
↓
ACTION_OPEN_DOCUMENT(SRT)
↓
takePersistableUriPermission
↓
parse
```

官方明确指出即使拿了 persistable permission，文件被移动或删除后仍可能需要重新授权。

所以 FilePermissionLost 必须是正常业务状态，不应该算异常 crash。

### OLED 真机实验矩阵

#### A. 最低舒适亮度，不测“最低看得见”

这是个很重要的区别。

M0A 现在验证的是：

能不能看见。

M0B/M1 应该开始验证：

连续看 20–60 分钟是否舒服。

建议组合：

- window：1 / 3 / 5 / 10 / 25%；
- glyph：RGB 2 / 4 / 8 / 16 / 32；
- 暖灰 / 琥珀 / 暗红；
- 20sp / 24sp / 30sp；
- medium weight。

不用全排列，使用逐步逼近：

太暗 → 加一级 → 舒适 → 再降一级确认。

记录“最低舒适值”。

#### B. 20 分钟阅读

素材必须包含：

- 中文；
- 英文；
- 日文；
- 双语；
- 超长句；
- 极短 cue；
- 连续快速 cue；
- 5–15 秒无字幕；
- emoji / 字体 fallback。

记录：

- 漏读；
- 字体笔画消失；
- 是否需要眯眼；
- 是否频繁调亮；
- 切换是否有拖影/色偏；
- 是否觉得字幕位置烦。

#### C. 60 分钟持续体验

关注：

- 阅读疲劳；
- 位置；
- 温度；
- 电量变化；
- 旁人是否注意到发光；
- 是否主动退出 Glow；
- 最终亮度和最初亮度是否一致。

项目种子本来也要求记录一小时温度、电量和旁观者感知。

#### D. 暂停 / 静态实验

不要故意高亮度烧屏。

使用正常校准值：

- 暂停 2 分钟；
- 暂停 5 分钟；
- 暂停 10 分钟；
- 随后显示均匀深灰画面观察暂时性残影。

这只能观察短期 image retention。

不能因此证明“长期不会烧屏”。

#### E. 系统干扰

必须真机测：

- 音量 overlay；
- 通知；
- 系统手势条；
- 充电提示；
- 来电；
- 闹钟；
- 耳机拔出；
- 蓝牙断开；
- Home；
- 电源键；
- 再次点亮；
- 进程被系统回收。

这些事件对这个产品尤其重要，因为一次系统白色弹层可能比正常字幕亮几十倍的主观感受。

#### F. 至少三类 OLED

现在已经有 vivo。

我建议进入公开 M1 前至少：

- 当前 vivo；
- Samsung AMOLED；
- Pixel 或另一类 LTPO OLED；

再加一台 LCD 对照。

Seed 原本给出的目标更严格，是 Pixel、Samsung、小米/Redmi、OPPO/OnePlus、vivo/iQOO 外加 LCD。

不一定 M0B 就全部凑齐，但公开发布前这个矩阵很合理。

## 11. 现在真正需要产品负责人决定的问题

我会把开放问题从现在文档里的大清单收敛为 10 个会真实阻塞 M1 设计的决定：

### ① M1 首个明确人群是谁？

建议：

有本地视频/音频 + SRT 的夜间观看者，优先外语内容。

不是泛播客用户。

### ② 准备页是否每次必经？

建议：否。

首次/异常时出现，正常 continue 跳过。

### ③ 单击是什么？

建议：显示/隐藏控制。

不要暂停。

### ④ 普通播放器默认显示上下文吗？

建议：是。

上一句 + 当前 + 下一句。

Glow 只当前。

### ⑤ M1 普通播放器显示视频画面吗？

建议：不显示。

视频只是时间源 + 音轨。

这是保护产品边界的一刀。

### ⑥ 双语默认开吗？

建议：单语默认，双语显式选择。

[I] 双语同时提升：

- 发光面积；
- 阅读负担；
- cue 高度；
- 烧屏区域；

语言学习用户再开启。

### ⑦ 字幕 offset 单步是多少？

没有足够证据。

VLC 用 50ms。

[H] 我会测试：

50ms / 100ms / 250ms

我预计 100ms 可能是手机操作更好的平衡，但现在不能固定。

### ⑧ 暂停多久以后字幕消失？

不能凭 OLED 理论直接决定。

测试：

30s→dim / 120s→hide
vs
60s→dim / 180s→hide

然后看用户是否频繁因为“我正在看这句，它怎么没了”而烦躁。

### ⑨ 字幕默认垂直位置？

现有文档倾向略低于中心。

[H] 仍然没有证据。

直接做三个 preset：

中央 / 略低 / 更低

连续阅读 20 分钟 A/B。

不要一开始做自由拖动。

### ⑩ 是否默认启用 anti-burn-in 位置漂移？

建议：M1 不默认。

先实验。

如果 60 分钟体验者普遍察觉不到，再考虑启用。

## 最终推荐的 M0B → M1 产品定义

如果让我现在把产品重新压成一句内部设计目标，我会写：

荧荧不是一个把播放器变黑的应用，而是一条从“选择媒体与字幕”逐渐退场到“只剩正在发生的文字”的路径。

具体来说：

Home 负责继续，Ready 负责排错，Normal Player 负责定位和校准，Glow 负责消失。

这四者职责越分明，产品越成立。

我认为当前文档里最应该立即修改的三项结论是：

- “准备页固定必经” → 改成条件式 Ready Resolver；
- “单击播放/暂停 vs 显示控制仍二选一” → 默认先采用单击显示控制；
- “周期性字幕位置移动是默认烧屏保护” → 降级为真机实验项。

而当前最应该坚持、不应继续讨论动摇的三件事是：

- 工作层和微光层严格分离；
- 播放器时间轴是字幕真相，字幕自己不跑时钟；
- M1 坚持本地媒体 + SRT，把 ASR、账号、媒体库、视频 Surface、TransVortex 自动互通全部挡在门外。

如果这套设计执行下去，M0B 最重要的 Go/No-Go 信号也会变得非常清晰：用户体验完那 3–5 分钟以后，是不是主动产生“我想把自己的内容放进去”的冲动。 如果没有，那么此时继续开发格式、媒体能力甚至云端能力都没有意义；这其实也正符合仓库种子原本设定的阶段门。
