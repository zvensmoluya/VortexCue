# 荧荧（VortexCue）布局与交互设计原则

> 本文描述荧荧 Android App 当前阶段的**布局结构、信息架构与交互设计思想**。
> 它不是视觉稿，也不是 Material 风格规范。现有 HTML 原型仅用于验证页面关系与功能边界，**不代表最终视觉气质**。
>
> 核心目标只有一个：
> **让复杂能力留在实现里，而不是长到用户界面上。**

---

## 1. 为什么需要这份设计

荧荧内部实际能力很多，包括：

* 本地媒体发现、扫描与授权
* 内容索引与可用性维护
* 播放顺序与播放状态恢复
* 外挂字幕、内嵌字幕与双字幕
* ASR 与翻译
* Glow 微光播放
* 显示校准
* 文件失效后的重新定位
* 来源刷新、权限恢复等异常处理

如果直接按照这些能力设计 UI，产品会迅速退化为：

> 文件管理器 + 媒体库 + 字幕工具 + AI 工作台 + 播放器 + 设置中心

这不是荧荧希望呈现给用户的产品。

因此，设计时必须区分：

1. **系统拥有什么能力**
2. **用户真正需要理解什么**
3. **用户什么时候必须做决定**
4. **哪些决定系统应该自动完成**

复杂度不应由功能数量决定，而应由**用户需要承担的决策数量**决定。

---

# 2. 总体设计原则

## 2.1 系统状态不等于用户界面

以下状态可以存在于数据模型，但不能因为存在就自动获得页面、Tab 或按钮：

* 待决定
* 已忽略
* 当前不可用
* URI 失效
* 字幕候选
* ASR 任务状态
* 翻译任务状态
* 网络等待
* Retry / Attempt
* Hash
* Token
* Provider 类型
* 字幕格式
* 文件来源类型

设计首先问：

> **用户是否真的需要对此做决定？**

如果答案是否定的，应优先自动处理。

## 2.2 异常流程不能定义主流程

字幕匹配失败、文件失效、权限丢失、生成失败等都是真实需求，但它们是少数情况。

不能因为 10% 的异常情况存在，就让 90% 的用户每天面对：

* 字幕绑定
* Provider
* 模型
* 任务
* 来源
* URI
* 重试
* 各种状态标记

主流程必须按照**自动成功**设计。

异常情况通过按需出现的纠错入口解决。

## 2.3 用户明确选择后，自动化退后

荧荧默认尽可能自动：

* 自动识别媒体
* 自动发现外挂字幕
* 自动识别内嵌字幕
* 自动判断主文字 / 第二文字
* 自动生成文字
* 自动恢复播放状态

但一旦用户明确手动选择过某个结果，例如手动指定某个字幕：

> **之后必须尊重用户选择，不允许系统偷偷替换。**

自动化负责减少操作，不负责覆盖用户意图。

## 2.4 Android-first，而不是桌面 Dashboard

荧荧是 Android App。

设计上优先采用移动端天然的层级：

* 底部一级导航
* 单列内容列表
* Bottom Sheet 承担临时动作
* 独立 Full-screen Player
* 沉浸式 Glow
* 清晰 Back Stack

避免：

* Dashboard
* 多栏布局
* 大量常驻面板
* 桌面工具式控制中心
* 每个能力都拥有独立页面

# 3. App 一级布局

当前一级结构：

```text
内容    播放列表    [荧荧 Logo]    配置    设置
```

其中：

* **内容**：一级页面
* **播放列表**：一级页面
* **荧荧 Logo**：动作入口，不是 Tab
* **配置**：一级页面
* **设置**：一级页面

播放器不进入底栏。

Glow 也不进入底栏。

## 3.1 为什么没有“首页”

荧荧目前没有：

* 推荐流
* 云端发现
* 社交 Feed
* 运营内容
* 个性化推荐

因此没有必要人为制造一个“首页”。

否则首页最终只会堆积：

* 最近
* 继续播放
* 播放列表
* 导入
* 任务
* 内容
* 设置捷径

这种页面没有独立用户目标，只是在重复其他空间。

App 默认进入 **内容** 即可。

当前播放状态由全局 Mini Player 承担，因此也不需要为了“继续播放”单独制造首页卡片。

---

# 4. 全局 App Shell

正常一级页面保持统一结构：

```text
┌──────────────────────────┐
│ Top App Bar              │
│                          │
│ 当前一级页面内容          │
│                          │
├──────────────────────────┤
│ Mini Player（播放时出现） │
├──────────────────────────┤
│ 内容 播放列表 Logo 配置 设置 │
└──────────────────────────┘
```

Mini Player 是唯一跨越一级页面的播放状态。

它负责：

* 当前内容标题
* 当前进度摘要
* 播放 / 暂停
* 进入 Normal Player

它不承担：

* 字幕管理
* 播放列表编辑
* Glow 设置
* 内容整理

---

# 5. 内容：用户自己的资源空间

## 5.1 内容页不是“媒体扫描结果”

`内容` 表示：

> **用户已经接受并整理进荧荧的内容。**

它不是 Android 文件系统的镜像，也不是扫描器的结果列表。

真实磁盘结构不能直接复制到这里。

例如真实设备可能是：

```text
Downloads/
├── DLsite/
├── Telegram/
├── ASMR/
│   ├── audio/
│   ├── subtitle/
│   └── cover/
└── ...
```

荧荧内部可以完全重新组织为：

```text
内容/
├── 睡前 ASMR/
├── 雨声/
├── 日语练习/
├── 夜雨耳语
├── 耳かき
└── Whisper Session
```

这两个空间必须解耦。

## 5.2 内容页本身就是根目录

不要设计一个额外的“未分类”分类。

没有进入虚拟文件夹的内容，直接存在于内容根目录。

例如：

```text
内容

睡前 ASMR                     32 >
雨声                           8 >

夜雨耳语
Circle Voice · 1:04:22

耳かき
Mio · 48:13

Whisper Session
Local Media · 56:08
```

因此：

* 虚拟文件夹位于根目录
* 普通内容也可以直接位于根目录
* 用户一个文件夹都不建时，内容页天然就是一整个列表

“未分类”只是内部可能存在的状态，不需要成为用户概念。

## 5.3 内容文件夹是虚拟整理结构

内容文件夹只用于用户自我整理。

它不是物理文件夹。

最低限度只需要：

* 新建
* 重命名
* 进入
* 把内容移动进去
* 把内容移回根目录
* 删除文件夹

初期不要增加：

* 标签系统
* 多层分类体系
* 文件夹颜色
* 智能分类
* 多标签归属
* 收藏体系

一个简单虚拟 Folder 已足够建立“这是我的内容空间”的感觉。

## 5.4 内容列表不制造假图片

荧荧当前没有明确的：

* 专辑封面体系
* 视频缩略图体系
* 艺术家头像
* 网络图片抓取

因此列表不应该为了套播放器模板而人为放置假封面。

内容项默认只显示文字信息：

```text
夜雨耳语
Circle Voice · 1:04:22
```

文件夹：

```text
睡前 ASMR                    32 >
```

这可以降低行高，提高信息密度，也更符合荧荧安静、工具化的产品气质。

## 5.5 内容项交互

### 单击

直接播放。

不要强制：

```text
内容 -> 详情 -> 播放
```

播放器最常见的动作就是播放。

### 长按 / 上下文菜单

提供低频操作：

* 立即播放
* 加入播放列表
* 移动到内容文件夹
* 同步文字
* 内容详情（如未来确实需要）
* 忽略

这类 secondary actions 不应常驻占据每一行。

## 5.6 搜索与排序

搜索不需要永久占据一整行。

推荐 Top App Bar：

```text
内容                        搜索  更多
```

点击搜索后切换为搜索模式：

```text
返回  搜索标题、作者、专辑
```

排序、显示已忽略等低频能力放入 overflow。

不要为这些能力制造二级 Tab。

---

# 6. 播放列表：只负责“当前播放顺序”

播放列表不维护另一套内容库。

它只回答：

> **接下来按照什么顺序播放？**

模型上可以直接把它理解为当前 Queue 的用户界面。

页面只需要：

* 查看当前项
* 选择任意项播放
* 调整顺序
* 移除
* 清空
* 下一项继续播放

例如：

```text
播放列表

≡ 夜雨耳语          当前播放
≡ 耳かき
≡ Sleep Talk
```

不要再建立：

* 播放列表库
* 多套保存播放列表
* Tonight 管理页
* Queue 管理页

如果未来使用“今晚”这个文案，它也只是当前播放列表的产品表达，不需要再建立新的系统概念。

---

# 7. 中间 Logo：Import Hub

中间的荧荧 Logo 是一个**动作入口**，不是页面导航。

它的设计职责相对较重，但职责是统一的：

> **负责荧荧与外部文件世界之间的边界。**

用户点击 Logo 后进入 Import Hub。

建议主要入口：

```text
添加内容

选择文件
从文件夹查找
扫描设备媒体

已添加的来源
ASMR Downloads
DLsite
...
```

## 7.1 Import Hub 负责什么

负责：

* 打开单个媒体
* 选择真实文件夹
* 扫描设备媒体
* 保存持续文件夹授权
* 查看已授权来源
* 重新扫描来源
* 重新授权
* 移除来源
* 把发现结果加入“内容”

这些都属于：

> 外部世界 -> 荧荧

因此放在一个入口是合理的。

## 7.2 Source 与 Content Folder 必须明确区分

### Source

真实世界的来源，例如：

```text
/storage/emulated/0/Download/ASMR/
```

只负责：

* 扫描
* 发现媒体
* 发现字幕
* 后续刷新

### Content Folder

荧荧内部的虚拟整理，例如：

```text
睡前 ASMR
```

只负责用户组织内容。

必须避免：

```text
Physical Folder -> 自动复制成 Virtual Folder
```

这种设计会让荧荧退化成文件管理器。

## 7.3 “新内容”不属于内容页

如果用户授权了持续来源，来源以后可能出现新的媒体。

例如：

```text
第一次：
01.mp4
02.mp4

之后：
03.mp4
04.mp4
```

荧荧可以在来源刷新后发现新增内容。

但不要在 `内容` 页面建立长期的：

* 待整理
* Inbox
* 新发现中心

更干净的方式：

```text
Logo
-> 已添加来源
-> 某个来源
-> 重新扫描
-> 本次发现
-> 选择加入
```

“待整理”可以是内部状态，但不应成为正式用户心智。

## 7.4 导入时只要求用户做真正属于他的决定

导入流程应该尽可能简单。

例如：

```text
找到 18 个媒体内容

✓ 夜雨耳语
✓ 耳かき
✓ Whisper 03
○ sample

放入：睡前 ASMR >

添加 17 项
```

用户主要只决定：

1. 哪些媒体我要
2. 放进哪个荧荧内容文件夹

不要要求用户在导入时进行字幕数据清洗。

---

# 8. 字幕 / 同步文字设计

这是目前设计中最重要的抽象之一。

## 8.1 正常情况下不存在“字幕绑定流程”

字幕绑定必须高度自动。

理想情况：

```text
媒体导入
-> 荧荧自动找到/准备文字
-> 直接可用
```

用户不需要知道：

* SRT
* ASS / SSA
* LRC
* WebVTT
* 内嵌轨
* 外挂字幕
* Candidate
* Binding
* Track ID

这些是实现概念。

## 8.2 用户心智只有“同步文字”

一个 Content 在 UI 中可以简单理解为：

```text
内容
├── 媒体
├── 主文字
└── 第二文字
```

主文字 / 第二文字背后可能来自：

* 外挂字幕
* 内嵌字幕
* ASR 结果
* 翻译结果

但 UI 不需要根据来源建立不同系统。

## 8.3 自动成功是主流程，手动选择只是纠错

如果系统自动匹配成功：

```text
同步文字
日本語 · 中文
```

用户无需操作。

如果没有文字：

```text
同步文字
暂无

生成文字
```

点击后：

```text
正在准备文字…
```

完成：

```text
同步文字
日本語 · 中文
```

不要暴露：

* ASR 进度细节
* chunk
* model
* token
* provider
* retry
* task queue

## 8.4 只有需要纠错时才进入“同步文字”页面

例如用户发现自动结果错了：

```text
同步文字

主文字
日本語

第二文字
中文

选择其他字幕文件
重新自动匹配
```

用户只负责：

* 换主文字
* 换第二文字
* 关闭某一文字
* 手动选择字幕文件
* 重新自动匹配

这个页面不是正常工作流，而是纠错工具。

## 8.5 不要让导入流程承担字幕确认

即使导入时发现多个字幕候选，也尽可能自动选择。

不要把：

```text
主字幕
第二字幕
候选 1
候选 2
语言
格式
```

塞进每次导入。

宁可先自动做一个高概率选择，真正播放发现错误时再让用户纠正。

设计原则：

> **不要因为系统没有 100% 把握，就把所有不确定性都转嫁给用户。**

---

# 9. ASR / 翻译：完全不透明的能力

用户操作：

```text
生成文字
```

荧荧内部可能发生：

```text
提取音轨
-> ASR
-> 翻译
-> 生成同步文字
-> 绑定主文字 / 第二文字
```

用户最多看到：

```text
正在准备文字…
```

然后：

```text
日本語 · 中文
```

失败时：

```text
生成失败
重试
```

不要设计：

* 任务中心
* 生成工作台
* 任务队列
* Pause / Resume UI
* attempt 详情
* token 详情
* hash
* Cue 数量
* 模型运行日志

这些信息即使内部存在，也没有资格成为普通 UI。

---

# 10. 配置：只负责连接信息

`配置` 页面当前只承担非常有限的职责。

## ASR

* OpenRouter Endpoint
* API Key

## LLM 翻译

* Endpoint
* API Key

仅此而已。

不要在这里建立：

* 方案系统
* Profile 系统
* Provider 工作台
* 模型目录
* Prompt 编辑器
* 任务管理
* 生成策略
* Retry Policy

如果未来某项能力真的成为用户频繁需要主动选择的东西，再重新评估。

不要因为底层支持，就提前暴露。

---

# 11. 设置：容纳应用级杂项

`设置` 不需要承担产品核心结构。

它就是 Android Settings。

适合放：

* Glow 字幕亮度
* 控制层亮度
* 字幕字号
* 字幕垂直位置
* 显示校准
* 播放行为
* Sleep Timer 默认行为
* 屏幕常亮
* 系统栏
* 权限
* 关于
* 其他长期偏好

原则：

> 低频、全局、长期偏好的东西进入设置。

不要为了让 Settings “漂亮”而把这些东西重新包装成一级功能。

---

# 12. Normal Player

播放器是播放状态，不是一级导航。

入口：

```text
Mini Player -> Normal Player
```

播放器负责：

* 播放 / 暂停
* 进度
* 前后跳转
* 上一项 / 下一项（如需要）
* 速度
* 字幕 offset
* 当前同步文字状态
* 当前播放列表入口
* 进入 Glow

Normal Player 可以比 Glow 信息更多，因为它本身就是准备与控制空间。

## 12.1 Player 中的同步文字

没有文字时，字幕舞台保留空白，只显示一个直接动作：

```text
生成同步文字
```

已有可翻译原文时，翻译只作为舞台边缘的上下文图标；任务开始后，该位置切换为环形进度。已有双语文字时不再显示生成、翻译或管理动作。

```text
当前原文
当前译文                    [译 / ◯]
```

主界面不出现“管理”。切换轨道、手动文件、恢复自动选择和低频时间偏移进入顶栏更多菜单中的同一套同步文字纠错页。

播放器不能拥有第二套字幕管理 UI。

---

# 13. Glow

Glow 是荧荧真正的沉浸模式。

进入 Glow 后：

* Bottom Navigation 消失
* Mini Player 消失
* Top App Bar 消失
* 系统栏隐藏
* Normal Player UI 消失
* 默认只剩同步文字

结构：

```text
Normal Player
      |
      v
    Glow
```

返回：

```text
Glow
 -> Normal Player
 -> 原来的一级页面
```

不要从 Glow 直接跳回首页或内容根目录。

## 13.1 Glow 中 UI 隐藏不是“极简审美”

Glow 减少 UI 的直接原因是：

> **减少发光像素。**

所以：

* 字幕间隙纯黑
* 控制层临时出现
* 几秒后自动隐藏
* 长按或手势唤起
* 控制亮度独立
* 暂停保护
* OLED 防残影策略

这些属于产品功能本身，而不是单纯视觉风格。

---

# 14. Navigation 与 Back Stack

推荐保持明确层级：

```text
Main Shell
├── 内容
├── 播放列表
├── 配置
└── 设置

Mini Player
    ↓
Normal Player
    ↓
Glow
```

Import Hub 属于临时动作层：

```text
Main Shell
    ↓
Logo
    ↓
Import Hub
    ↓
Import Flow / Source
```

内容文件夹：

```text
内容
 -> 文件夹
 -> 返回内容原位置
```

原则：

* 返回时尽量恢复原 Tab
* 恢复原滚动位置
* Player 退出回到原页面
* Glow 退出回 Player
* 临时 Bottom Sheet 不改变一级导航位置

---

# 15. 异常状态如何出现

异常状态应“就地出现”，而不是创建异常管理中心。

例如媒体失效：

```text
夜雨耳语
文件不可用
```

点击后：

```text
重新定位
```

来源授权失效：

```text
Logo
-> 来源
-> 需要重新授权
```

生成失败：

```text
生成失败
重试
```

不要为了这些异常建立：

* 不可用内容中心
* 权限任务中心
* 失败任务中心
* 恢复工作台

除非未来真实用户行为证明有必要。

# 16. 视觉设计与布局设计必须分离

当前 HTML 原型只验证：

* 页面层级
* 导航
* 内容密度
* 信息优先级
* 操作入口
* 主流程与异常流程

它的：

* 灰白配色
* 圆角
* 图标
* 字体
* Bottom Bar 样式
* 卡片风格
* 间距
* 动画

都不是最终视觉规范。

正式 UI 应重新根据荧荧品牌气质设计。

因此开发时应把原型理解为：

> **结构参考，不是像素参考。**

# 17. 新增功能时的判断规则

未来任何新能力进入 UI 前，都先回答以下问题。

## 17.1 这是新用户意图，还是完成旧意图的新实现？

例如：

* 增加 WebVTT 支持
  -> 仍然只是“同步文字”
  -> 不增加 UI

* 增加新的 ASR Provider
  -> 仍然只是“生成文字”
  -> 不增加普通 UI

* 增加字幕语言识别
  -> 让自动匹配更好
  -> 应减少 UI，而不是增加 UI

## 17.2 这是 90% 主流程，还是 10% 修复流程？

如果只是：

* 字幕匹配错
* 文件失效
* 来源授权失败
* 生成失败

应优先设计成按需出现。

不能让异常状态决定主界面结构。

## 17.3 用户必须理解这个概念吗？

如果用户不需要理解：

* URI
* Track
* Provider
* Endpoint 类型
* Task
* Candidate
* Hash
* Attempt
* Cue

这些概念就不能作为主要 UI taxonomy。

## 17.4 能不能自动？

只要可以高概率自动完成，就先自动。

用户真正应该花精力的地方主要是：

* 哪些内容属于我
* 我怎么整理这些内容
* 接下来播什么
* 自动结果错了时怎么纠正

这才是荧荧应该让用户思考的事情。

# 19. 最终设计判断

荧荧内部可以是一台复杂的机器。

但用户看到的产品应该只是：

> **把本地内容放进来，按自己的方式整理，选择接下来听什么，然后进入微光。**

同步文字应该尽可能自己准备好。

文件来源应该尽可能自己维护。

播放状态应该尽可能自己恢复。

只有系统无法可靠替用户做决定时，才请求用户介入。

这就是当前布局设计的核心：

> **复杂性属于实现，决定权属于用户，操作负担不应该属于用户。**
